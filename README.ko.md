## 왜 Akasha 인가

Akasha 는 또 하나의 에이전트가 아닙니다. 이미 쓰는 AI 안에서 돕니다. 스킬이 팀 절차를 알려 주고, 훅이 절차를 깨는 동작을 막고, 단계 관문이 통과 전까지 과업을 붙잡습니다.

| | 없으면 | Akasha 가 있으면 |
|:--|:--|:--|
| 팀 규칙 | 사람마다 AI 가 제각각 일합니다 | 관리자가 `akasha.toml` 에 한 번 적습니다.<br>팀의 모든 AI 와 서버 검사가 그 규칙을 따릅니다 |
| 모호한 요청 | AI 가 다른 기능을 만듭니다 | 완료 조건이 분명해질 때까지 AI 가 묻습니다.<br>그 전엔 과업이 넘어가지 않습니다 |
| 기술 판단 | 개발자만 판단할 수 있습니다 | AI 가 판단하고 기록합니다.<br>사람은 무엇을, 어떻게 보이게, 어떻게 쓰게 할지만 정합니다 |
| 부작용 | 무엇을 더 건드리는지 아무도 모릅니다 | 기능·데이터·API·다른 과업에 대한 영향과<br>되돌리는 방법을 AI 가 기록합니다 |
| "다 됐어요" | 말뿐입니다 | 요청자가 미리보기로 써 보고<br>조건마다 수용합니다 |
| 몇 달 뒤 | 문제를 일으킨 변경을 못 찾습니다 | 변경마다 스쿼시 커밋 하나와<br>1분 브리핑 |
| 같은 기능, 두 사람 | 한 사람이 기다립니다 | 두 번째 과업이 첫 과업 위에 쌓입니다 |

## 빠른 시작

**1. 관리자 — 레포마다 한 번**

플러그인을 설치하고, 레포를 열고, **"Akasha 설정해줘"** 라고 말합니다.

```
/plugin marketplace add Gruci/akasha-team-harness
/plugin install akasha@akasha
```

AI 가 다음을 묻습니다.

- 팀 규칙을 관리할 관리자
- 위험하게 다룰 폴더와, 그 폴더의 변경을 승인할 사람
- 프로젝트를 설치하고, 테스트하고, 미리보기로 띄우는 명령

그다음 GitHub 설정 변경을 승인합니다. AI 가 팀 전체에 서버 규칙을 켜고, 설정 파일을 담은 PR 을 엽니다. 그 PR 을 병합합니다.

**2. 팀원 각자 — 한 번**

같은 플러그인을 설치하고 팀 레포를 엽니다. 세션이 시작되면 Akasha 훅이 레포를 확인하고 결과를 AI 에게 넘깁니다.

| 훅이 찾은 것 | 일어나는 일 |
|:--|:--|
| 아직 설정 전 | AI 가 1단계의 설정을 안내합니다 |
| 서버 규칙이 꺼져 있음 | AI 가 알려 줍니다. 관리자가 한 번 승인하면 AI 가 켭니다.<br>작업은 바로 시작하고, 인계만 기다립니다 |
| 준비됨 | AI 가 바로 일을 시작합니다. 설정할 것 없음 |

**3. 기능을 요청합니다**

```
고객 검색에 날짜 필터 넣어 줘.
```

> **참고:** Python 3.11 이상, git, GitHub 가 필요합니다. Codex 는 `pip install "git+https://github.com/Gruci/akasha-team-harness@v1.0.0"` 도 필요합니다.

## 얻는 것

<p align="center"><img src="docs/readme/team.ko.svg" width="1000" alt="세 사람이 한 레포에서 동시에, 각자 자기 AI 와 일합니다. Akasha 의 공유 작업 보드가 같은 기능인 내보내기 버튼을 날짜 필터 위에 쌓고, 청구서 과업은 동시에 진행되게 합니다. GitHub 가 커밋 세 개를 차례로 병합합니다: #41, #42, #43."></p>

관리자가 레포를 한 번 설정해 두었습니다. 그 뒤 같은 날 오후, 세 사람이 변경을 요청합니다. 각자 자기 AI 하고만 이야기합니다. 셋 다 개발자가 아닙니다.

| 누가 | 요청 | 공유 작업 보드 |
|:--|:--|:--|
| 운영팀,<br>Claude Code 로 | "고객 검색에 날짜 필터 넣어 줘." | 새 과업. 작업 사본이 따로 생깁니다 |
| 재무팀,<br>Claude Code 로 | "청구서에 세금 보여 줘." | 날짜 필터와 겹치지 않아<br>동시에 진행합니다 |
| 영업팀, Codex 로,<br>조금 뒤에 | "고객 검색에 내보내기 버튼 넣어 줘." | 날짜 필터와 같은 기능.<br>그 브랜치에서 시작하고,<br>날짜 필터가 병합된 뒤에 인계합니다 |

GitHub 가 커밋 세 개를 차례로 병합합니다 — `#41 Show the tax on invoices`, `#42 Add a date filter`, `#43 Add an export button`. 커밋마다 브리핑이 따로 붙습니다. 아무도 다른 사람의 답을 기다리지 않았습니다.

두 과업이 겹치면 보드가 정합니다.

| 겹침 | 일어나는 일 |
|:--|:--|
| 같은 기능 | 새 과업이 앞 과업 위에 쌓입니다 |
| 같은 파일 | 앞 과업이 먼저 병합됩니다 |
| 같은 계약 | 상대 과업의 이슈에 알림이 남고,<br>GitHub 가 그 이슈를 지켜보는 사람에게 알립니다 |

과업마다 보드의 이슈, 미리보기 포트, 미리보기 데이터베이스도 따로 갖습니다.

## 동작 방식

<p align="center"><img src="docs/readme/stages.ko.svg" width="1000" alt="여섯 단계와 단계 사이의 Akasha 관문: 요청, 명세, 구현, 검사, 검수, 인계. 모든 단계의 일은 AI 가 합니다. 요청자가 답하고, 승인하고, 수용합니다. 세 번 실패하면 개발자가 봅니다. GitHub 가 병합합니다."></p>

| 단계 | 통과 조건 | AI 말고 누가 |
|:--|:--|:--|
| 첫 과업 전 | 팀 규칙이 `akasha.toml` 에 있다.<br>첫 인계 전에 서버 규칙이 켜져 있다 | 관리자, 한 번 |
| 1. 요청 | 완료 조건이 분명하다 | 요청자가 질문에 답합니다 |
| 2. 명세 | 영향도가 기록됐다.<br>요청자가 승인한다 | 요청자가 승인합니다 |
| 3. 구현 | 범위 안의 파일만 바뀌었다 | — |
| 4. 검사 | 필수 검사를 모두 통과한다 | 세 번 고쳐도 안 되면<br>개발자 |
| 5. 검수 | 요청자가 미리보기에서 수용한다.<br>제품 지도에 변경이 반영됐다 | 요청자가 수용합니다 |
| 6. 인계 | 서버 검사를 통과한다.<br>브리핑과 함께 커밋 하나로 병합된다 | GitHub 가 병합합니다 |

작은 수정은 `small`, 버그는 `fix` 워크플로로 갑니다.

| 층 | 지키는 것 |
|:--|:--|
| 작업 중 | 훅이 모든 명령과 저장한 파일을 검사합니다.<br>강제 push 처럼 되돌릴 수 없는 동작을 막습니다 |
| 인계 직전 | 통과 조건.<br>브리핑 검사도 포함합니다 |
| 서버 | 필수 검사 `akasha` 가 기본 브랜치의 규칙으로 돕니다.<br>PR 이 자기 규칙을 느슨하게 고칠 수 없습니다 |

## 누가 무엇을

| 누구 | 하는 일 | 할 필요 없는 일 |
|:--|:--|:--|
| **관리자** | 레포를 한 번 설정합니다: 팀 규칙을 `akasha.toml` 에.<br>GitHub 설정 변경을 승인합니다 | 설정을 하나하나 손으로 맞추기 |
| **요청자** — 팀원 누구나 | 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지 말합니다.<br>미리보기를 써 봅니다 | 코드 읽기, 기술 위험 판단 |
| **AI** — Claude Code 나 Codex | 구현, 범위, 영향도, 테스트.<br>브리핑과 제품 지도 | 사람에게 기술 질문하기 |

## 서버 규칙

GitHub 고유의 보호가 먼저입니다. Akasha 보조 워크플로는 GitHub 요금제에 그 기능이 없을 때만 빈자리를 채웁니다.

| 레포 | 지키는 것 |
|:--|:--|
| 공개 레포, 또는<br>GitHub Pro·Team·Enterprise 의 비공개 레포 | **GitHub** — 브랜치 보호, 필수 검사,<br>코드 오너, 자동 병합 |
| GitHub Free 의 비공개 레포 | **Akasha 보조 도구** — `akasha-merge` 가 검사 통과 뒤 병합합니다.<br>`akasha-watch` 가 검사를 건너뛴 변경을 되돌리고 이슈를 엽니다 |

설정은 GitHub 부터 시도하고, 어느 쪽이 적용되는지 `akasha.toml` 에 기록합니다. 요금제를 바꿨다면 설정을 다시 돌리면 됩니다.

> **참고:** GitHub 는 나쁜 변경을 병합 전에 막고, `akasha-watch` 는 들어온 직후에 되돌립니다. 관리자 push 와 강제 push 는 되돌리지 않고 알리기만 합니다.

## 보장하는 것과 보장하지 않는 것

| 보장하는 것 | 어떻게 |
|:--|:--|
| 관리자 없이 팀 규칙이 바뀌지 않는다 | CODEOWNERS |
| 필수 검사에 실패한 변경은 병합되지 않는다 | 서버 규칙. 설정이 설치하고,<br>세션을 시작할 때마다 다시 확인합니다 |
| 요청자가 수용하지 않은 것은 PR 로 넘어가지 않는다 | `feature`·`fix` 는 수용 기록이 있어야<br>인계합니다 |
| 모든 변경을 찾아서 되돌릴 수 있다 | 과업마다 브리핑을 담은 스쿼시 커밋 하나 |
| 과업끼리 덮어쓰지 않는다 | 과업마다 작업 사본 하나.<br>같은 기능의 과업은 쌓입니다 |

| 보장하지 않는 것 | 알아 둘 것 |
|:--|:--|
| 미리보기 환경 | 프로젝트가 제공합니다. 관리자가 설정 때 명령을 알려 주고,<br>AI 가 그 명령으로 띄웁니다 |
| 보안 경계 | 훅은 협조하는 AI 를 규칙 위에 두는 장치입니다.<br>샌드박스가 아닙니다 |
| 업무 로직의 정확성 | 그건 검수가 봅니다 |
| 데이터 되돌림 | 코드를 되돌려도 데이터는 돌아오지 않습니다.<br>되돌리는 방법은 영향도 기록에 있습니다 |

| 두 사람이 같은 기능을 바꾸면요? | 두 번째 과업이 첫 과업 위에 쌓입니다.<br>첫 요청자가 수용한 동작을 바꾸면,<br>Akasha 가 GitHub 에 그 사람 앞으로 알림을 남깁니다 |
| 변경은 어떻게 되돌리나요? | 기본 브랜치에서 그 커밋을 찾아 브리핑을 읽습니다.<br>그 커밋 하나를 되돌립니다 |

## 자세히

시작하는 데는 필요 없습니다 — AI 가 알아서 다룹니다.

<details>
<summary><b>안을 들여다보면 — 네 영역, 여덟 부품</b></summary>

| 영역 | 부품 | 하는 일 |
|:--|:--|:--|
| 작업 절차 | Core | 과업 상태, 단계 이동, PR 브리핑 |
| 작업 절차 | Workflow | `feature`·`fix`·`small` 의 단계와 통과 조건 |
| 작업 절차 | Skills · Context | 절차, 제품 지도, 팀의 결정 |
| 작업 절차 | Validators | 기계로 잴 수 있는 규칙을 검사로 |
| 작업 절차 | Team Config | `akasha.toml` 의 팀 규칙 |
| 에이전트 엔진 | Agent Engine | Claude Code 나 Codex 에 훅과 스킬을 연결 |
| 조정 | Coordinator | 공유 작업 보드, 겹침 검사, 과업 쌓기 |
| 인프라 관리 | Infra Manager | 서버 규칙을 Team Config 와 같게 유지 |

```
akasha/
├── core/          과업 상태, 단계, 위험, 작업 사본, PR 글
├── workflows/     feature · fix · small
├── validators/    가드, 비밀키 검사, 검사 실행기, 브리핑 검사, 언어 팩
├── coordinator/   공유 작업 보드, 겹침 검사, 미리보기 자원
├── infra/         GitHub 설정, merge·watch 보조 도구, 워크플로 틀
└── engine/        Claude Code·Codex 훅
skills/            akasha-setup · akasha-request · akasha-inspect · akasha-handover
```

</details>
