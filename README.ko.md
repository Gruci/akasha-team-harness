## 팀이 Akasha 를 쓰는 이유

AI 에이전트는 누구에게나 코드를 써 줍니다. 팀에서는 그 때문에 새로운 문제가 생깁니다.
Akasha 는 그 문제를 개발자에게 닿기 전에 막습니다.

| Akasha 없이 | Akasha 와 함께 |
|:--|:--|
| 팀원이 AI 에게 기능을 요청합니다. 요청이 모호해서 AI 가 다른 기능을 만듭니다 | Akasha 가 완료 조건이 분명해질 때까지 묻습니다 |
| AI 가 "다 됐어요"라고 합니다. 팀원이 원하던 동작인지 아무도 모릅니다 | 팀원이 미리보기로 기능을 확인하고 수용합니다 |
| 고객 데이터나 권한을 건드리는 변경인데 아무도 위험을 보지 못합니다 | Akasha 가 위험 등급을 매기고, 위험이 크면 개발자 승인을 받습니다 |
| 개발자가 설명 없는 큰 PR 을 받습니다 | 모든 PR 에 요청 내용, 테스트 결과, 수용 결과, 남은 위험이 담깁니다 |
| 두 사람이 같은 기능을 동시에 바꿉니다 | Akasha 가 작업이 시작되기 전에 겹침을 찾습니다 |
| 팀의 규칙이 선임 개발자의 머릿속에만 있습니다 | 규칙이 레포에 있고, 모든 변경에서 검사가 지킵니다 |

## 요청 하나가 병합되기까지

운영팀의 요청자가 고객 검색에 날짜 필터를 넣고 싶어 합니다. 요청자는 개발자가 아닙니다.

1. **요청자가 요청합니다.** "고객 검색에 날짜 필터 넣어 줘."
2. **Akasha 가 되묻습니다.** "가입일인가요, 거래일인가요?" "권한 없는 고객도 보여야 하나요?" "기존 필터와 함께 쓰이나요?"
3. **Akasha 가 만들고 검사합니다.** 에이전트 엔진이 과업 전용 작업 사본에서 변경을 만들고, Akasha 가 테스트와 검사를 돌리며 실패를 고칩니다.
4. **요청자가 확인합니다.** Akasha 가 예시 데이터로 필터를 미리보기에 띄우고, 요청자가 결과를 수용합니다.
5. **개발자가 병합합니다.** PR 에 위험 등급 낮음, 테스트 전부 통과, 요청자 수용이 적혀 있습니다. 개발자는 데이터 권한과 쿼리 속도를 보고 병합합니다.

요청자는 코드를 쓰지 않았고, 개발자는 절차를 다시 설명하지 않았습니다. 그 일은 Akasha 가 했습니다.

## 누가 무엇을 하나

| 사람 | 하는 일 | 할 필요가 없는 일 |
|:--|:--|:--|
| 요청자 | 목표를 말하고, 업무 질문에 답하고, 미리보기를 확인합니다 | 코드 읽기, 명령 실행, 구조 결정 |
| 개발자 | 위험이 큰 설계를 승인하고, PR 을 리뷰하고, 병합합니다 | 요청마다 절차를 다시 설명하기 |
| 관리자 | 팀 규칙을 `akasha.toml` 에 한 번 적습니다 | 레포 설정을 하나하나 손으로 맞추기 |

질문은 답할 수 있는 사람에게만 갑니다. 요청자는 기술 질문을 받지 않습니다.

## Akasha 는 이렇게 동작합니다

Akasha 는 에이전트 엔진을 정해진 절차 안에 넣습니다.
모든 과업은 여섯 단계를 거치고, 통과 조건을 채워야 다음 단계로 갑니다.

| 단계 | 통과 조건 |
|:--|:--|
| 1. 요청 | 완료 조건이 분명하다 |
| 2. 명세·위험 | 요청자가 설계를 승인한다. 위험이 크면 개발자도 승인한다 |
| 3. 구현 | 허용된 파일·도구·권한만 썼다 |
| 4. 검사·복구 | 필수 검사를 모두 통과한다. 세 번 고쳐도 안 되면 Akasha 가 멈추고 쉬운 말로 개발자에게 알린다 |
| 5. 검수 | 요청자가 미리보기에서 결과를 수용한다 |
| 6. 인계 | 개발자가 승인하고 필수 검사가 통과하면 병합된다 |

작은 수정은 `small` 워크플로로, 버그는 `fix` 워크플로로 갑니다.

Akasha 는 이 절차를 세 겹으로 지킵니다.

1. **작업 중** — 파일을 저장할 때와 턴이 끝날 때마다 검사합니다. 강제 push 처럼 되돌릴 수 없는 명령은 실행 전에 막습니다.
2. **인계 직전** — 필수 검사와 테스트가 통과하고 요청자가 수용해야 PR 이 열립니다.
3. **서버** — Akasha 가 GitHub 의 필수 검사, 브랜치 보호, CODEOWNERS 를 설치하고 지켜봅니다. 필수 검사는 기본 브랜치의 규칙으로 돌기 때문에, 검사를 느슨하게 고친 PR 은 통과하지 못합니다.

## 설치

Akasha 는 플러그인입니다. Claude Code 에서 두 줄을 입력합니다.

```
/plugin marketplace add Gruci/akasha-team-harness
/plugin install akasha@akasha
```

그다음 이렇게 합니다.

1. 레포를 엽니다.
2. "Akasha 설정해줘"라고 말합니다.
3. 팀의 역할, 위험하게 다룰 영역, 미리보기 명령에 대한 질문에 답합니다.

Akasha 가 `akasha.toml` 을 쓰고, GitHub 를 설정하고, Codex 가 읽는 파일도 씁니다.

> **주의:** 브랜치 보호와 CODEOWNERS 는 레포 관리자가 승인할 때만 바꿉니다.

Python 3.11 이상과 git 이 필요합니다. PR 흐름과 서버 규칙에는 GitHub 가 필요합니다.

## Akasha 안에 있는 것

Akasha 는 네 영역, 여덟 부품으로 이루어집니다.

| 영역 | 부품 | 하는 일 |
|:--|:--|:--|
| 팀 하네스 | Core | 과업 상태를 지키고, 단계를 옮기고, 승인 대기를 잡고, 인계 문서를 씁니다. 팀마다 바뀌지 않는 부분입니다 |
| 팀 하네스 | Workflow | 단계와 통과 조건을 선언합니다. `feature`·`fix`·`small` 을 팀이 고치고 더합니다 |
| 팀 하네스 | Skills · Context | 팀 고유의 절차와 지식만 둡니다. 요청 인터뷰, 결정과 교훈의 기록 같은 것입니다 |
| 팀 하네스 | Validators | 기계로 잴 수 있는 규칙을 검사로 바꿉니다 — 테스트, 린트, 경계 검사, 비밀키, 되돌릴 수 없는 명령 |
| 팀 하네스 | Team Config | 레포 하나의 팀 규칙을 `akasha.toml` 에 둡니다 — 역할, 위험 규칙, 승인 규칙, 워크플로, 검사, 미리보기 명령 |
| 에이전트 엔진 | Agent Engine | Akasha 의 세션 규칙·훅·스킬로 Claude Code 나 Codex 를 구동합니다 |
| 조정 | Coordinator | GitHub 에 공유 작업 보드를 두고, 작업이 시작되기 전에 겹침을 찾고, 과업마다 미리보기 자원을 나눕니다 |
| 인프라 관리 | Infra Manager | 필수 검사, 브랜치 보호, CODEOWNERS 를 Team Config 와 같게 유지하고, 바뀐 설정은 되돌리자고 제안합니다 |

## 팀이 바꿀 수 있는 것

- **에이전트 엔진** — Claude Code 나 Codex. 절차와 검사는 그대로입니다.
- **언어** — Python·TypeScript·Go·Java 팩이 들어 있고, 다른 언어는 팩 파일 하나로 붙입니다.
- **워크플로** — 고치고 더해도 코어는 바뀌지 않습니다.
- **프로젝트 구조** — 레이어형이든 기능 단위든 강요하지 않습니다.

## Akasha 가 보장하는 것

| 보장하는 것 | 어떻게 |
|:--|:--|
| 필수 검사에 실패한 변경은 병합되지 않는다 | 필수 검사와 브랜치 보호가 막고, Akasha 가 이것을 설치하고 지켜봅니다 |
| 위험이 큰 변경은 개발자 승인 없이 병합되지 않는다 | 위험 등급이 승인자를 정하고 CODEOWNERS 가 강제합니다 |
| 요청자가 수용하지 않은 기능은 PR 로 넘어가지 않는다 | `feature`·`fix` 워크플로에서 6단계는 5단계의 수용 기록이 있어야 시작합니다 |
| 두 과업이 서로의 작업을 덮어쓰지 않는다 | 과업마다 작업 사본이 따로 있고, Akasha 가 시작 전에 겹침을 찾습니다 |

| 보장하지 않는 것 | 이유 |
|:--|:--|
| 업무 로직의 정확성 | 검수와 리뷰가 봐야 합니다. 테스트가 맞는 동작을 다루는지는 사람이 판단합니다 |
| 보안 경계 | 로컬 검사는 협조하는 에이전트 엔진을 규칙 위에 두는 장치이지 샌드박스가 아닙니다 |
| 미리보기 환경 | 프로젝트가 제공합니다. Akasha 는 프로젝트의 명령으로 띄우고 과업마다 이름을 나눕니다 |

## 자주 묻는 질문

| 질문 | 답 |
|:--|:--|
| 개발자가 없는 팀도 쓸 수 있나요? | 아니요. 병합은 개발자가 결정해야 합니다. Akasha 는 그 결정을 바로 내릴 수 있는 상태로 결과를 만듭니다 |
| 요청자는 터미널을 써야 하나요? | 아닙니다. 데스크톱 앱에서 말로 요청하면 됩니다. 명령은 Akasha 가 실행합니다 |
| 인프라 규칙은 누가 바꾸나요? | 레포 관리자만 바꿉니다. Akasha 는 변경을 제안하고, 관리자가 승인한 뒤에 바꿉니다 |
| 두 요청자가 같은 것을 바꾸려 하면요? | 두 번째 과업이 시작되기 전에 Akasha 가 겹침을 찾습니다. 같은 기능이면 합류를 제안하고, 같은 파일이면 순서를 정하고, 같은 계약이면 담당자에게 알립니다 |
| 테스트가 없는 레포에도 쓸 수 있나요? | 쓸 수 있지만 4단계의 보장이 약해집니다. Team Config 에서 테스트를 필수 검사로 지정하면 테스트 없는 병합을 막습니다 |
