## 팀이 Akasha 를 쓰는 이유

AI 에이전트는 누구에게나 코드를 써 줍니다. 팀에서는 그 때문에 새로운 문제가 생깁니다.
Akasha 는 팀 전체가 쓰는 하네스이고, 팀원 각자가 설치합니다. Akasha 는 그 문제를 막아서, 개발자와 다른 팀원이 하나의 제품을 함께 만들게 합니다.

| Akasha 없이 | Akasha 와 함께 |
|:--|:--|
| 변경의 기술적 영향은 개발자만 판단할 수 있습니다 | AI 가 기술 판단을 내리고 기록합니다. 사람은 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지만 정합니다 |
| 팀원이 AI 에게 기능을 요청합니다. 요청이 모호해서 AI 가 다른 기능을 만듭니다 | Akasha 가 완료 조건이 분명해질 때까지 묻습니다 |
| AI 가 "다 됐어요"라고 합니다. 팀원이 원하던 동작인지 아무도 모릅니다 | 팀원이 미리보기로 기능을 확인하고 수용합니다 |
| 변경이 다른 기능, 고객 데이터, 권한을 건드리는데 아무도 영향을 보지 못합니다 | AI 가 다른 기능·데이터·API 에 대한 영향을 찾고, 되돌리는 방법까지 기록합니다 |
| 설명 없이 병합되어서, 나중에 문제를 일으킨 변경을 아무도 찾지 못합니다 | 모든 변경이 1분 브리핑(이유, 범위, 영향 범위, 검증)을 본문으로 한 커밋 하나로 병합됩니다 |
| 두 사람이 같은 기능을 동시에 바꾸고, 서로를 기다립니다 | Akasha 가 작업이 시작되기 전에 겹침을 찾고, 두 번째 과업을 첫 과업 위에 쌓아서 아무도 기다리지 않습니다 |

## 요청 하나가 병합되기까지

운영팀의 요청자가 고객 검색에 날짜 필터를 넣고 싶어 합니다. 요청자는 개발자가 아닙니다.

1. **요청자가 요청합니다.** "고객 검색에 날짜 필터 넣어 줘."
2. **Akasha 가 되묻습니다.** "가입일인가요, 거래일인가요?" "권한 없는 고객도 보여야 하나요?" "기존 필터와 함께 쓰이나요?"
3. **AI 가 영향을 살핍니다.** 보고서 두 개도 고객 테이블을 읽습니다. 이번 변경은 인덱스를 더하고 데이터는 바꾸지 않습니다. AI 가 이 영향도 분석을 기록합니다.
4. **Akasha 가 만들고 검사합니다.** AI 가 과업 전용 작업 사본에서 변경과 조건마다의 테스트를 만들고, Akasha 가 검사를 돌리며 AI 가 실패를 고칩니다.
5. **요청자가 확인합니다.** Akasha 가 예시 데이터로 필터를 미리보기에 띄우고, 요청자가 결과를 수용합니다.
6. **GitHub 가 병합합니다.** PR 에는 1분 브리핑이 있습니다. 서버 검사가 통과하면 GitHub 가 변경을 커밋 하나로 병합합니다.

요청자는 코드를 쓰지도, 기술 판단을 내리지도 않았습니다. 아무도 절차를 설명하지 않았습니다. 그 일은 Akasha 와 AI 가 했습니다.

## 누가 무엇을 하나

| 누구 | 하는 일 | 할 필요가 없는 일 |
|:--|:--|:--|
| 요청자 (개발자든 아니든 팀원 누구나) | 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지 말하고 미리보기를 확인합니다 | 코드 읽기, 구현 결정, 기술 위험 판단 |
| AI (에이전트 엔진) | 구현·범위·영향도를 결정하고, 테스트·브리핑·제품 지도를 씁니다 | 사람에게 기술 질문하기 |
| 관리자 | 팀 규칙을 `akasha.toml` 에 한 번 적고, GitHub 설정 변경을 승인합니다 | 레포 설정을 하나하나 손으로 맞추기 |

Akasha 는 사람에게 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지만 묻습니다.

## Akasha 는 이렇게 동작합니다

Akasha 는 에이전트 엔진을 정해진 절차 안에 넣습니다.
모든 과업은 여섯 단계를 거치고, 통과 조건을 채워야 다음 단계로 갑니다.

| 단계 | 통과 조건 |
|:--|:--|
| 1. 요청 | 완료 조건이 분명하다 |
| 2. 명세·영향도 | 요청자가 명세를 승인한다. AI 가 기능·데이터·API·다른 과업에 대한 영향과 되돌리는 방법을 기록했다 |
| 3. 구현 | 범위 안의 파일만 바꿨다 |
| 4. 검사·복구 | 필수 검사를 모두 통과한다. 세 번 고쳐도 안 되면 Akasha 가 멈추고 쉬운 말로 개발자에게 알린다 |
| 5. 검수 | 요청자가 미리보기에서 결과를 수용한다. 제품 지도에 변경이 반영됐다 |
| 6. 인계 | 서버 검사가 통과하면 GitHub 가 브리핑을 본문으로 한 커밋 하나로 병합한다 |

작은 수정은 `small` 워크플로로, 버그는 `fix` 워크플로로 갑니다.

Akasha 는 이 절차를 세 겹으로 지킵니다.

1. **작업 중** — 파일을 저장할 때와 턴이 끝날 때마다 검사합니다. 강제 push 처럼 되돌릴 수 없는 명령은 실행 전에 막습니다.
2. **인계 직전** — 필수 검사가 통과하고, 요청자가 수용하고, 브리핑이 검사를 통과해야 PR 이 열립니다.
3. **서버** — Akasha 가 GitHub 의 필수 검사, 브랜치 보호, 자동 병합을 설치하고 지켜봅니다. 필수 검사는 기본 브랜치의 규칙으로 돌기 때문에, 검사를 느슨하게 고친 PR 은 통과하지 못합니다. 팀 규칙을 바꾸는 변경은 관리자가 승인해야 합니다.

## 설치

Akasha 는 팀 하네스입니다. 팀원 각자가 설치합니다. Claude Code 에서 두 줄을 입력합니다.

```
/plugin marketplace add Gruci/akasha-team-harness
/plugin install akasha@akasha
```

레포마다 한 사람이 한 번 설정합니다.

1. 레포를 엽니다.
2. "Akasha 설정해줘"라고 말합니다.
3. 관리자, 위험하게 다룰 영역, 미리보기 명령에 대한 질문에 답합니다.

Akasha 가 `akasha.toml` 과 제품 지도를 쓰고, GitHub 를 설정하고, Codex 가 읽는 파일도 씁니다. 그다음 팀원 각자가 레포를 열고 기능을 요청합니다.

> **주의:** 브랜치 보호, 자동 병합, CODEOWNERS 는 레포 관리자가 승인할 때만 바꿉니다.

Python 3.11 이상과 git 이 필요합니다. PR 흐름과 서버 규칙에는 GitHub 가 필요합니다.

## Akasha 안에 있는 것

Akasha 는 네 영역, 여덟 부품으로 이루어집니다.

| 영역 | 부품 | 하는 일 |
|:--|:--|:--|
| 작업 절차 | Core | 과업 상태를 지키고, 단계를 옮기고, PR 브리핑을 씁니다. 팀마다 바뀌지 않는 부분입니다 |
| 작업 절차 | Workflow | 단계와 통과 조건을 선언합니다. `feature`·`fix`·`small` 을 팀이 고치고 더합니다 |
| 작업 절차 | Skills · Context | 절차, 제품 지도, 팀의 결정을 둡니다 |
| 작업 절차 | Validators | 기계로 잴 수 있는 규칙을 검사로 바꿉니다 — 테스트, 린트, 범위, 비밀키, 브리핑, 되돌릴 수 없는 명령 |
| 작업 절차 | Team Config | 레포 하나의 팀 규칙을 `akasha.toml` 에 둡니다 — 역할, 위험 규칙, 사람 관문, 워크플로, 검사, 미리보기 명령 |
| 에이전트 엔진 | Agent Engine | Akasha 의 세션 규칙·훅·스킬로 Claude Code 나 Codex 를 구동합니다 |
| 조정 | Coordinator | GitHub 에 공유 작업 보드를 두고, 작업이 시작되기 전에 겹침을 찾고, 같은 기능의 과업을 쌓고, 과업마다 미리보기 자원을 나눕니다 |
| 인프라 관리 | Infra Manager | 필수 검사, 브랜치 보호, 자동 병합, CODEOWNERS 를 Team Config 와 같게 유지하고, 바뀐 설정은 되돌리자고 제안합니다 |

## 팀이 바꿀 수 있는 것

- **에이전트 엔진** — Claude Code 나 Codex. 절차와 검사는 그대로입니다.
- **언어** — Python·TypeScript·Go·Java 팩이 들어 있고, 다른 언어는 팩 파일 하나로 붙입니다.
- **워크플로** — 고치고 더해도 코어는 바뀌지 않습니다.
- **사람 관문** — 기본은 AI 가 기술 판단을 내립니다. 데이터 변경에 개발자 승인처럼, 위험 수준마다 사람 관문을 더할 수 있습니다.
- **프로젝트 구조** — 레이어형이든 기능 단위든 강요하지 않습니다.

## Akasha 가 보장하는 것

| 보장하는 것 | 어떻게 |
|:--|:--|
| 필수 검사에 실패한 변경은 병합되지 않는다 | 필수 검사와 브랜치 보호가 막고, Akasha 가 이것을 설치하고 지켜봅니다 |
| 팀 규칙을 바꾸는 변경은 관리자 없이 병합되지 않는다 | CODEOWNERS 가 팀 규칙을 관리자에게 줍니다 |
| 요청자가 수용하지 않은 기능은 PR 로 넘어가지 않는다 | `feature`·`fix` 워크플로에서 6단계는 5단계의 수용 기록이 있어야 시작합니다 |
| 모든 변경을 찾아서 되돌릴 수 있다 | 과업마다 스쿼시 커밋 하나로 병합되고, 그 본문이 브리핑(이유, 범위, 영향 범위, 검증)입니다 |
| 두 과업이 서로의 작업을 덮어쓰지 않는다 | 과업마다 작업 사본이 따로 있고, 같은 기능의 과업은 앞 과업 위에 쌓입니다 |

| 보장하지 않는 것 | 이유 |
|:--|:--|
| 업무 로직의 정확성 | 검수가 봐야 합니다. 결과가 팀에 필요한 일을 하는지는 사람이 판단합니다 |
| 데이터 되돌림 | 코드를 되돌려도 데이터는 돌아오지 않습니다. 데이터 변경을 되돌리는 방법은 영향도 분석에 기록됩니다 |
| 보안 경계 | 로컬 검사는 협조하는 에이전트 엔진을 규칙 위에 두는 장치이지 샌드박스가 아닙니다 |
| 미리보기 환경 | 프로젝트가 제공합니다. Akasha 는 프로젝트의 명령으로 띄우고 과업마다 이름을 나눕니다 |

## 자주 묻는 질문

| 질문 | 답 |
|:--|:--|
| 개발자가 없는 팀도 쓸 수 있나요? | 네. 기술 판단은 AI 가 내리고, 실패한 변경은 서버 검사가 막습니다. 개발자가 있는 팀은 데이터나 권한에 사람 관문을 더하면 됩니다 |
| 요청자는 터미널을 써야 하나요? | 아닙니다. 데스크톱 앱에서 말로 요청하면 됩니다. 명령은 Akasha 가 실행합니다 |
| 인프라 규칙은 누가 바꾸나요? | 레포 관리자만 바꿉니다. Akasha 는 변경을 제안하고, 관리자가 승인한 뒤에 바꿉니다 |
| 두 사람이 같은 기능을 바꾸려 하면요? | 두 번째 과업이 시작되기 전에 Akasha 가 겹침을 찾고, 두 번째 과업을 첫 과업 위에 쌓아서 아무도 서로를 기다리지 않습니다. 두 번째 요청이 첫 요청자가 수용한 동작을 바꾸면, Akasha 가 GitHub 에서 첫 요청자에게 알립니다 |
| 변경은 어떻게 되돌리나요? | 기본 브랜치에서 그 커밋을 찾습니다. 브리핑에 이유, 범위, 영향 범위가 있습니다. 그 커밋 하나를 되돌립니다. 데이터 변경이면 영향도 분석의 되돌리는 방법도 따릅니다 |
| 테스트가 없는 레포에도 쓸 수 있나요? | 네. AI 가 완료 조건마다 테스트를 씁니다. Team Config 에서 테스트를 필수 검사로 지정하면 테스트 없는 병합을 막습니다 |
