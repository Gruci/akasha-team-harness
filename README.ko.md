## 왜 Akasha 인가

AI 에이전트는 누구에게나 코드를 써 줍니다. 팀에서 문제는 코드가 아니라 코드를 둘러싼 모든 것입니다.

| Akasha 없이 | Akasha 와 함께 |
|:--|:--|
| 변경의 기술적 영향은 개발자만 판단할 수 있습니다 | **AI 가 판단하고 기록합니다.** 사람은 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지만 정합니다 |
| 요청이 모호해서 AI 가 다른 기능을 만듭니다 | **먼저 묻습니다.** 완료 조건이 분명해질 때까지 Akasha 가 묻습니다 |
| AI 가 "다 됐어요"라고 하지만 맞는지 아무도 모릅니다 | **요청자가 검수합니다.** 미리보기로 확인하고 수용합니다 |
| 변경이 다른 기능이나 데이터를 건드리는데 아무도 모릅니다 | **AI 가 영향을 찾습니다.** 기능·데이터·API·다른 과업에 대한 영향과 되돌리는 방법을 기록합니다 |
| 나중에 문제를 일으킨 변경을 아무도 찾지 못합니다 | **커밋 하나, 브리핑 하나.** 모든 변경이 1분 브리핑(이유, 범위, 영향 범위, 검증)과 함께 병합됩니다 |
| 두 사람이 같은 기능을 바꾸며 서로를 기다립니다 | **아무도 기다리지 않습니다.** 두 번째 과업이 첫 과업 위에 쌓입니다 |

## 빠른 시작

**1. 설치합니다.** 팀원 각자, 한 번:

```
/plugin marketplace add Gruci/akasha-team-harness
/plugin install akasha@akasha
```

**2. 팀 레포를 엽니다.** Akasha 가 먼저 GitHub 에서 레포를 확인합니다.

| Akasha 가 찾은 것 | 일어나는 일 |
|:--|:--|
| 팀 규칙과 서버 규칙이 켜져 있음 | 바로 준비된 것입니다. 아무도 설정하지 않습니다 |
| 레포가 아직 Akasha 를 쓰지 않음 | **"Akasha 설정해줘"** 라고 말합니다. 관리자, 위험하게 다룰 영역, 미리보기 명령을 묻습니다 |
| 서버 규칙이 꺼져 있음 | Akasha 가 알려 줍니다. 레포 관리자가 팀 전체를 위해 한 번 켭니다 |

**3. 평소 말로 기능을 요청합니다.**

```
고객 검색에 날짜 필터 넣어 줘.
```

> **참고:** Python 3.11 이상, git, GitHub 가 필요합니다. Codex 는 `pip install "git+https://github.com/Gruci/akasha-team-harness@v1.0.0"` 도 필요합니다.

## 얻는 것

개발자가 아닌 운영팀원의 요청 하나:

```
요청자   ─►  "고객 검색에 날짜 필터 넣어 줘."
Akasha   ─►  "가입일인가요, 거래일인가요?"
             "권한 없는 고객도 보여야 하나요?"
AI       ─►  보고서 두 개도 고객 테이블을 읽는다는 것을 찾음
             기록: 인덱스 추가, 데이터 변경 없음, 커밋을 되돌리면 원상 복구
AI       ─►  과업 전용 작업 사본에서 변경과 조건마다의 테스트를 만듦
Akasha   ─►  검사 ─► 미리보기 ─► 요청자 수용
GitHub   ─►  커밋 하나로 병합: "Add a date filter (#42)" + 브리핑
```

요청자는 코드를 쓰지도, 기술 판단을 내리지도 않았습니다. 아무도 절차를 설명하지 않았습니다.

## 동작 방식

모든 과업은 여섯 단계를 거치고, 통과 조건을 채워야 다음 단계로 갑니다.

```
요청 ──► 명세 ──► 구현 ──► 검사 ──► 검수 ──► 인계
 │        │        │        │        │        │
완료조건  영향도    범위 안   검사     수용 +    병합됨
분명     기록      파일만    통과     제품 지도
```

| 단계 | 통과 조건 |
|:--|:--|
| 1. 요청 | 완료 조건이 분명하다 |
| 2. 명세·영향도 | 요청자가 승인한다. AI 가 기능·데이터·API·다른 과업에 대한 영향과 되돌리는 방법을 기록했다 |
| 3. 구현 | 범위 안의 파일만 바꿨다 |
| 4. 검사·복구 | 필수 검사를 모두 통과한다. 세 번 고쳐도 안 되면 Akasha 가 멈추고 쉬운 말로 개발자에게 알린다 |
| 5. 검수 | 요청자가 미리보기에서 수용한다. 제품 지도에 변경이 반영됐다. 서버 규칙이 켜져 있다 |
| 6. 인계 | 서버 검사가 통과하면 브리핑을 본문으로 한 커밋 하나로 병합된다 |

작은 수정은 `small` 워크플로로, 버그는 `fix` 워크플로로 갑니다.

이 절차를 세 겹으로 지킵니다.

| 층 | 지키는 것 |
|:--|:--|
| 작업 중 | 훅이 명령과 저장한 파일을 하나하나 검사합니다. 강제 push 처럼 되돌릴 수 없는 명령은 실행 전에 막습니다 |
| 인계 직전 | 통과 조건. 브리핑도 검사를 통과해야 합니다 |
| 서버 | 필수 검사 `akasha` 가 기본 브랜치의 규칙으로 돌기 때문에, PR 이 자기 규칙을 느슨하게 고칠 수 없습니다 |

## 누가 무엇을

| 누구 | 하는 일 | 할 필요가 없는 일 |
|:--|:--|:--|
| **요청자** — 개발자든 아니든 팀원 누구나 | 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지 말하고 미리보기를 확인합니다 | 코드 읽기, 구현 결정, 기술 위험 판단 |
| **AI** — Claude Code 나 Codex | 구현·범위·영향도를 결정하고 테스트·브리핑·제품 지도를 씁니다 | 사람에게 기술 질문하기 |
| **관리자** | 팀 규칙을 `akasha.toml` 에 한 번 적고, GitHub 설정 변경을 승인합니다 | 레포 설정을 하나하나 손으로 맞추기 |

Akasha 는 사람에게 무엇을 만들지, 어떻게 보일지, 어떻게 쓸지만 묻습니다.

## 서버 규칙

GitHub 고유의 브랜치 보호와 자동 병합이 먼저입니다. Akasha 보조 도구는 GitHub 요금제에 그 기능이 없을 때만 빈자리를 채웁니다.

| 레포 | 규칙을 지키는 것 |
|:--|:--|
| 공개 레포, 또는 GitHub Pro·Team·Enterprise 의 비공개 레포 | **GitHub** — 브랜치 보호, 필수 검사, 코드 오너, 자동 병합 |
| GitHub Free 의 비공개 레포 | **Akasha 보조 도구** — `akasha-merge` 가 검사 통과 뒤 PR 을 병합하고, `akasha-watch` 가 검사를 거치지 않은 변경을 되돌리고 이슈를 엽니다 |

설정은 GitHub 보호부터 시도하고 결과를 `akasha.toml` 에 기록합니다. 보조 도구는 늘 설치되어 있고, GitHub 가 기본 브랜치를 보호하는 동안에는 아무것도 하지 않습니다. 그래서 요금제를 바꾼 레포는 설정 한 번으로 규칙도 바뀝니다.

> **참고:** GitHub 보호는 나쁜 변경을 병합 전에 막고, `akasha-watch` 는 들어온 직후에 되돌립니다. 관리자의 push 와 강제 push 는 되돌리지 않고 알리기만 합니다.

## 안을 들여다보면

Akasha 는 네 영역, 여덟 부품으로 이루어집니다.

| 영역 | 부품 | 하는 일 |
|:--|:--|:--|
| 작업 절차 | Core | 과업 상태를 지키고, 단계를 옮기고, PR 브리핑을 씁니다 |
| 작업 절차 | Workflow | 단계와 통과 조건을 선언합니다: `feature`·`fix`·`small` |
| 작업 절차 | Skills · Context | 절차, 제품 지도, 팀의 결정을 둡니다 |
| 작업 절차 | Validators | 기계로 잴 수 있는 규칙을 검사로 바꿉니다 |
| 작업 절차 | Team Config | 팀 규칙을 `akasha.toml` 에 둡니다 |
| 에이전트 엔진 | Agent Engine | Akasha 의 훅과 스킬로 Claude Code 나 Codex 를 구동합니다 |
| 조정 | Coordinator | 공유 작업 보드를 두고, 겹침을 찾고, 같은 기능의 과업을 쌓습니다 |
| 인프라 관리 | Infra Manager | 서버 규칙을 확인하고 Team Config 와 같게 유지합니다 |

```
akasha/
├── core/          과업 상태, 단계, 위험, 작업 사본, PR 글
├── workflows/     feature · fix · small
├── validators/    가드, 비밀키 검사, 검사 실행기, 브리핑 검사, 언어 팩
├── coordinator/   공유 작업 보드, 겹침 검사, 미리보기 자원
├── infra/         GitHub 설정, merge·watch 보조 도구, 워크플로 틀
└── engine/        Claude Code·Codex 훅
skills/            akasha-setup · akasha-request · akasha-inspect · akasha-handover
```

## Akasha 가 보장하는 것

| 보장하는 것 | 어떻게 |
|:--|:--|
| 필수 검사에 실패한 변경은 병합되지 않는다 | 서버 규칙이 막고, Akasha 가 이것을 설치하고 지켜봅니다 |
| 팀 규칙을 바꾸는 변경은 관리자 없이 병합되지 않는다 | CODEOWNERS 가 팀 규칙을 관리자에게 줍니다 |
| 요청자가 수용하지 않은 기능은 PR 로 넘어가지 않는다 | `feature`·`fix` 워크플로에서 인계는 수용 기록이 있어야 시작합니다 |
| 모든 변경을 찾아서 되돌릴 수 있다 | 과업마다 브리핑을 담은 스쿼시 커밋 하나로 병합됩니다 |
| 두 과업이 서로의 작업을 덮어쓰지 않는다 | 과업마다 작업 사본이 따로 있고, 같은 기능의 과업은 앞 과업 위에 쌓입니다 |

| 보장하지 않는 것 | 이유 |
|:--|:--|
| 업무 로직의 정확성 | 검수가 봐야 합니다 |
| 데이터 되돌림 | 코드를 되돌려도 데이터는 돌아오지 않습니다. 데이터 변경을 되돌리는 방법은 영향도 분석에 기록됩니다 |
| 보안 경계 | 로컬 검사는 협조하는 AI 를 규칙 위에 두는 장치이지 샌드박스가 아닙니다 |
| 미리보기 환경 | 프로젝트가 제공합니다. Akasha 는 프로젝트의 명령으로 띄웁니다 |

## 자주 묻는 질문

| 질문 | 답 |
|:--|:--|
| 개발자가 없는 팀도 쓸 수 있나요? | 네. 기술 판단은 AI 가 하고, 실패한 변경은 서버 검사가 막습니다. 개발자가 있는 팀은 데이터나 권한에 사람 관문을 더할 수 있습니다 |
| 요청자는 터미널을 써야 하나요? | 아닙니다. 데스크톱 앱에서 말로 요청합니다. 명령은 Akasha 가 실행합니다 |
| 두 사람이 같은 기능을 바꾸려 하면요? | 두 번째 과업이 첫 과업 위에 쌓여서 아무도 기다리지 않습니다. 첫 요청자가 수용한 동작을 바꾸면 Akasha 가 GitHub 에서 그 사람에게 알립니다 |
| 변경은 어떻게 되돌리나요? | 기본 브랜치에서 그 커밋을 찾습니다. 브리핑에 이유, 범위, 영향 범위가 있습니다. 그 커밋 하나를 되돌립니다 |
| GitHub Free 의 비공개 레포도 되나요? | 네. Akasha 의 merge·watch 보조 도구가 규칙을 지킵니다. [서버 규칙](#서버-규칙)을 보세요 |
